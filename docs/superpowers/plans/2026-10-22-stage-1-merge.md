# Stage 1: Merge Offer Portal work Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make this repo (the Complete portal baseline) a single working app that carries the Offer Portal's post-fork improvements and can stand up on a fresh database.

**Architecture:** The Complete portal was remixed from the Offer Portal on 2026-08-31 and shared its database, so its migrations start on 2026-08-31 and assume tables the Offer Portal created (`deals`, `rep_profiles`, `user_roles`, `has_role`, …). Stage 1 restores those base migrations, proves the full chain applies to an empty database, then ports the four Offer Portal commits made after the fork (Lovable commits `474bea4`, `cc2970d`, `c1ab28b`, `007f013`, 2026-10-19 to 2026-10-21).

**Tech Stack:** TanStack Start 1.168, React 19, Tailwind 4, shadcn/ui, Supabase (Postgres + Auth), Vitest 4, Bun.

**Spec:** `docs/superpowers/specs/2026-10-22-magenta-combined-portal-design.md` (sections 5, 7, 8 step 1, 10)

**Source of ported code:** the Offer Portal export, referred to below as `OFFER/` (the unzipped `4afedcc5-…_1.zip`; in the original session it lives at `/tmp/claude-0/-home-user-highstone/a8215db4-37a6-5c5a-a9b8-b808cadbe2f2/scratchpad/offer`). It can also be read through the Lovable MCP (`read_file`, project `4afedcc5-cb3c-4d59-a4a8-cab3059ebd38`).

## Global Constraints

- Never commit `.env` or any key. `.env.example` lists the variable names.
- Every admin server function calls `assertAdmin(context)` first, before reading input-dependent data.
- An admin can never remove their own admin role or turn off their own sign-in (`assertNotSelfLockout`).
- Password rule: at least 8 characters (`MIN_PASSWORD_LENGTH = 8`) and confirmation must match.
- Existing tests keep passing: `delivery-state`, `phone`, `schedule`, `portal-routing`, `schedule-ui`, `deals.tap-targets`, `offer.tap-targets`.
- Do not change product behavior beyond this plan; lifecycle, merchant hub and design work belong to stages 2–4.
- Leave fonts as they are in this stage. (The repo uses Manrope/Sora; the Offer Portal used Questrial/Jost. The owner decides in stage 4.)

## Review Focus

1. **Migrations applied to an empty database in timestamp order.** The Offer base migrations (2026-08-28…08-30) must run before the Complete migrations (2026-08-31…). Any migration that assumes data or an object created by hand in the old database fails. Covered by Task 2's check.
2. **An admin disabling or demoting themself.** Must be refused on the server, not only hidden in the UI. Covered by Task 3's tests on `assertNotSelfLockout` plus the server function call order.
3. **A reset link opened twice, or after it expires.** The second visit must show "This link has expired or was already used" with a "Send a new link" button, never a blank form. Covered by Task 5's `parseRecoveryHash` tests.
4. **A partner member (not a rep) opening `/reset-password` while signed in.** Must go to `/portal/settings`, not to the internal `/account`. Covered by Task 5's `signedInResetTarget` test.
5. **Sign out, then press Back.** No signed-in page or cached data reappears. Covered by Task 4's manual check and the `replace: true` navigation.
